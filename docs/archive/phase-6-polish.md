# Phase 6 Completion — Post-Assessment Polish

Phase 6 fixes three issues identified during the code assessment review of Phases 1–5. No new features — these are correctness and robustness improvements.

---

## What Was Fixed

### 1. Rate Limit Backoff Holds HTTP Connection Open

**File:** `backend/internal/connectors/logs/supabase.go` (modified)

**Problem:** `queryAPI()` checked rate limit headers and slept *before* calling `io.ReadAll(resp.Body)`. If the Supabase API returned `X-RateLimit-Remaining: 0` with a reset window of several minutes, the HTTP response body remained open for the entire backoff duration, tying up the underlying TCP connection in the HTTP client pool.

**Fix:** Reordered the logic — body is now read immediately after the response arrives, then status codes are checked, and only after the body is fully consumed does the rate limit backoff sleep occur. The HTTP connection is released back to the pool before any waiting happens.

**Before:**
```
receive response → check rate limit headers → sleep → read body → check status
```

**After:**
```
receive response → read body → check status → check rate limit headers → sleep
```

The rate limit backoff still blocks the *current poll cycle* from returning (preventing a subsequent request while rate limited), but no longer holds a transport-level connection.

### 2. UpdateConnection Doesn't Restart Poller

**File:** `backend/internal/api/handlers/connections.go` (modified)

**Problem:** When a user edited a Supabase connection — changing the poll interval, access token, project ref, or polled tables — the existing polling goroutine continued running with the old config. Only `CreateConnection` started a poller and `DeleteConnection` stopped one. Users had to delete and recreate the connection to apply config changes.

**Fix:** After `UpdateConnection` successfully writes to the database, it now:
1. Stops any existing poller for the connection ID (also handles the case where a connection type changes *away* from Supabase).
2. If the updated type is `"supabase"`, creates a new `Supabase` connector from the updated config and starts a fresh polling goroutine.

This mirrors the pattern already used in `CreateConnection`.

### 3. LIKE Wildcard Characters Not Escaped in Search Queries

**Files:**
- `backend/internal/agent/tools_logs.go` (modified) — new `escapeLike()` helper, applied to query values
- `backend/internal/db/queries/log_buffer.sql` (modified) — added `ESCAPE '\'` clause
- `backend/internal/db/log_buffer.sql.go` (auto-generated)

**Problem:** The `SearchLogsByUser` and `SearchLogsByUserAndSeverity` queries used `ILIKE '%' || $2 || '%'`. While the parameter binding prevents SQL injection, the LIKE pattern metacharacters `%` and `_` in the search term were interpreted as wildcards. An agent searching for a literal `%` or `_` (common in URL-encoded payloads, database identifiers, etc.) would get unexpected broad matches.

**Fix:**

**New helper** in `tools_logs.go`:
```go
func escapeLike(s string) string {
    s = strings.ReplaceAll(s, `\`, `\\`)
    s = strings.ReplaceAll(s, `%`, `\%`)
    s = strings.ReplaceAll(s, `_`, `\_`)
    return s
}
```

**SQL update** — both search queries now include `ESCAPE '\'`:
```sql
WHERE payload::text ILIKE '%' || @query::text || '%' ESCAPE '\'
```

The `escapeLike()` function is called on the query string before it is passed to the sqlc-generated function, so `%`, `_`, and `\` in user input are treated as literal characters.
