# v0.46.0 Deploy Runbook

**Applies to:** any environment deploying commit `18153bd` (Phases 1–5 of source filtering) where migration 035 has not yet been applied.

**Why a runbook:** migration 035 adds `connections.org_id NOT NULL` with a backfill step, and migration 036 drops the `github_repos` table after migrating its rows. Both are one-way in practice and need concurrent writers stopped for the window. The pre-flight check catches a specific edge case (orphan `applications.org_id IS NULL`) that would abort 035 mid-migration.

---

## Before the deploy

### 1. Check whether this runbook applies

```bash
psql "$DATABASE_URL" -c "SELECT version FROM schema_migrations ORDER BY version::int DESC LIMIT 1;"
```

- If the highest version is **≥ 35**: migration 035 has already been applied. Skip the pre-flight and writer-quiescence steps — they only matter *during* application of 035. Normal `make migrate-up` is fine for 036/037 (they don't have the same orphan risk). **Still run the post-migration sanity check in step 5** — environments that applied 035 before this runbook existed (e.g. staging on commit `18153bd`) may have raced against concurrent writers and produced orphan `connections.org_id IS NULL` rows that failed the migration partially. A zero count confirms the landing was clean; a non-zero count means manual repair before proceeding.
- If the highest version is **< 35**: continue.

### 2. Run the pre-flight check

```bash
psql "$DATABASE_URL" -f docs/archive/runbooks/v0.46.0-preflight.sql
```

Expected output: `NOTICE: v0.46.0 pre-flight OK. Safe to run migrate-up.`

If the script raises an exception, stop. Inspect the orphan rows with the diagnostic query printed in the exception, repair the data (typically by reassigning `applications.org_id`), and re-run the pre-flight until it passes. **Do not edit migration 035 to work around this** — migrations are immutable once committed to master.

## During the deploy

### 3. Stop concurrent writers

Migration 035 cannot take a `LOCK TABLE` inside its own transaction that persists across the migrator's separate statements — `make migrate-up` uses golang-migrate which commits each migration in its own tx, so a LOCK in one wouldn't protect the next. The practical answer is to stop writes for the duration of the migration window.

**Fly.io:**
```bash
fly scale count 0 --app heimdall
```

**Other platforms:** scale API replicas to zero, or put the service behind a maintenance page.

**Also quiesce indirect writer paths.** Scaling the primary app to zero stops API-initiated `INSERT INTO connections` calls, but any sidecar or third-party service that pushes traffic into our webhook ingestion endpoint also produces writes (via `UpsertConnectionSource` on source-discovery) and races migration 035 the same way. Before proceeding:

- **Fly.io Log Shipper** (`heimdall-log-shipper` or equivalent org-wide drain): `fly scale count 0 --app heimdall-log-shipper` — or, if the shipper serves multiple tenants, route it away from this Heimdall instance for the migration window.
- **Any org-scoped webhook forwarder** (GitHub App webhook replay, custom shippers): pause at the source if controllable; otherwise accept that the window is short enough that replay queues will drain after the migration completes.
- **Syslog / OTLP listeners** live inside the primary app process, so they're already quiesced by `fly scale count 0`.

**Size the downtime window** before scaling down so the outage is planned, not measured:

```sql
SELECT count(*) FROM connections;
```

Migration 035 UPDATEs every row then takes an ACCESS EXCLUSIVE on the ALTER. At a few thousand rows the window is seconds; at 100k+ rows plan minutes. At the current user base this is seconds — but measure before deploy, don't guess.

### 4. Run migrations

```bash
set -a && . ./.env && set +a && make migrate-up
```

Watch for: `35/u org_connections`, `36/u github_to_generic_sources`, `37/u source_filter_lookup_index` applied cleanly.

### 5. Post-migration sanity checks

```sql
-- 035: no null org_ids
SELECT count(*) FROM connections WHERE org_id IS NULL;  -- expect 0

-- 036: github_repos table gone, rows migrated
SELECT to_regclass('public.github_repos');  -- expect NULL
SELECT count(*) FROM app_source_filters asf
  JOIN connections c ON c.id = asf.connection_id
  WHERE c.type = 'github';  -- expect >= number of previously-enabled github_repos rows

-- 037: both partial indexes present
SELECT indexname FROM pg_indexes
  WHERE tablename = 'app_source_filters'
  AND indexname LIKE 'idx_app_source_filters%';
-- expect both idx_app_source_filters_lookup AND idx_app_source_filters_app_lookup
```

## After the deploy

### 6. Restart writers

```bash
fly scale count N --app heimdall  # or whatever the pre-deploy count was
```

### 7. Communicate drop-by-default to existing users

Migrations 034–036 do not auto-enable any source. Existing webhook / OTLP / syslog integrations must explicitly enable their source names via the new "Manage Sources" selector or their traffic will be dropped. Send a short note to any active users pointing at the connection detail modal's new button.

## Rollback

If the deploy goes wrong mid-flight:

- **Before 035 commits:** pre-flight failed or the migrator errored before `COMMIT` — no schema change was made. Fix forward.
- **After 035 commits but before 036:** `make migrate-down` once reverts 035 destructively (deletes all org-scoped connections, which at this point would be zero since the app hasn't been upgraded yet). Safe.
- **After 036 commits:** `github_repos` is gone. The down migration of 036 synthesises negative `repo_id`s to rebuild the UNIQUE constraint — functional but not a faithful restoration. Prefer **fixing forward** over rolling back at this point.
- **After 037 commits:** trivially reversible (`make migrate-down` drops the new index).

---

## Lessons from Phase 5 review

The pre-flight check and the explicit "stop writers" step are the procedural fix for the Phase 5 review's Tier 1.1 finding. The review initially suggested editing `035_org_connections.up.sql` in place to add `LOCK TABLE` and a pre-flight `DO` block; we rejected that because migrations are immutable once committed, and editing an applied migration file causes schema drift vs `schema_migrations`' recorded state on environments where it has already run. The runbook is the honest answer.
